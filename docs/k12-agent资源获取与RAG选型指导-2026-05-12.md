# K12 教学 Agent 资源获取与 RAG 选型指导 - 2026-05-12

## 1. 结论

当前 K12 教学 Agent 项目在资源获取层面，**不应默认把向量数据库作为基础必选项**。

更适合的 2026 开发路径是：

- **结构化资源**优先使用 `PostgreSQL`
- **外部系统能力**优先封装为 `Skill / API`
- **会话态与缓存**优先使用 `Redis`
- **语义相似检索场景**再引入 `Vector DB / RAG`

换句话说，主流方向不是“彻底不用 RAG”，而是：

> **不再把 RAG 当成 Agent 的默认底座，而是按场景选择检索方式。**

---

## 2. 2026 常见 Agent 架构趋势

过去常见模式是：

```text
文档切块 -> embedding -> 向量检索 -> 拼接上下文 -> LLM
```

2026 更常见的模式是：

```text
Agent
-> Structured Data (SQL / PostgreSQL)
-> Tool / Skill / MCP / API
-> Full-text / Keyword Search
-> Long Context
-> Optional Vector Retrieval
-> LLM
```

核心变化：

1. **不再先建向量库再说**
2. **RAG 仍然存在，但只是检索工具箱中的一种**
3. **Long context 能力增强后，中小规模知识场景可以先不上向量库**
4. **更多项目采用混合检索：标签过滤 + 全文检索 + 向量检索 + rerank**

---

## 3. 对本项目的判断

结合当前项目定位（K12 教学工作流、多业务 Agent、教育资源与外部系统接入），推荐采用以下判断原则。

### 3.1 优先使用 PostgreSQL 的资源

适合放在结构化数据库中的内容：

- 课程标准
- 教材目录
- 知识点体系
- 题库元数据
- 学生基础档案
- 班级信息
- 作业记录
- 考试成绩
- 错题记录
- 教案模板索引

这类数据特点：

- 字段清晰
- 可按 `grade / subject / topic / class_id / student_id` 精确过滤
- 结果可解释性强
- 更适合业务约束和权限控制

### 3.2 优先使用 Skill / API 的能力

适合走外部接口封装的内容：

- 校本资源平台
- 作业平台
- 考试系统
- 用户中心
- 通知系统
- 学生画像系统

原则：

- Agent 不直接请求外部系统
- 外部系统能力沉淀为 `Skill`
- Skill 负责鉴权、参数转换、异常处理、重试和响应清洗

### 3.3 优先使用 Redis 的数据

适合放 Redis 的内容：

- 用户会话上下文
- 多轮澄清状态
- 热点资源缓存
- 最近检索结果缓存
- LLM 响应缓存
- 限流计数
- 临时任务状态

### 3.4 适合使用 Vector DB / RAG 的内容

只有在以下场景中，向量数据库才具备明显价值：

- 教材正文切片的语义召回
- 相似教案检索
- 教学活动案例检索
- 教研资料与课件文本检索
- 题目解析、错题解析的相似讲解检索
- 教师经验案例、家校沟通话术库的语义召回

这些内容通常具备如下特点：

- 以非结构化长文本为主
- 用户问题表达自然，难以用固定字段筛选
- 目标不是精确查某条记录，而是找“最相关片段”
- 需要跨来源内容统一召回

## 4. “是否需要向量数据库”的判断标准

可直接使用以下标准判断。

### 4.1 不需要向量数据库的情况

满足以下多数条件时，建议先不上向量库：

- 资源总量不大
- 资源具备清晰标签，如 `grade / subject / topic`
- 查询目标本质上是结构化事实
- 已知候选范围较小
- 可以通过 SQL 过滤或全文检索快速定位
- 主要需求是流程编排，而不是大规模知识召回

此时推荐方案：

```text
Agent
-> Service
-> PostgreSQL / Skill / Redis
-> keyword/full-text search
-> long context
-> LLM
```

### 4.2 建议引入向量数据库的情况

当满足以下 2 条及以上时，可考虑引入向量库：

- 非结构化文本资源明显增多
- 关键词检索召回效果差
- 用户输入自然语言跨度大，不适合固定条件过滤
- 需要跨教材、教案、案例、解析统一检索
- 很难确定应把哪段材料放入 Prompt
- 召回质量已成为生成质量瓶颈

此时推荐方案：

```text
Agent
-> ResourceService
   -> metadata filter
   -> keyword/full-text retrieval
   -> vector retrieval
   -> rerank
-> LLM
```

## 5. 对本项目的推荐开发路径

### 5.1 第一阶段：先不上向量库

现阶段建议优先建设以下主链路：

```text
Agent -> Service -> Repository / Skill -> PostgreSQL / API / Redis
```

优先目标：

1. 资源访问分层清晰
2. 结构化教育资源先可用
3. 外部系统能力先打通
4. 工作流先稳定运行
5. Agent 具备基础可解释性与可控性

建议优先补充的模块：

```text
src/services/
  resource_service.py
  curriculum_service.py
  textbook_service.py
  lesson_plan_service.py
  question_bank_service.py
  student_profile_service.py
  learning_analytics_service.py

src/repositories/
  postgres_repository.py
  redis_repository.py

src/skills/
  resource_platform_skill.py
  homework_platform_skill.py
  exam_system_skill.py
  school_user_skill.py
```

### 5.2 第二阶段：先做轻量检索能力

在不引入向量库前，可先做：

- metadata filter
- keyword search
- full-text search
- 候选内容拼接到 long context
- 结果缓存

适用场景：

- TeachingDesignAgent 根据年级、学科、主题查课程标准与教材片段
- HomeworkAgent 查题库元数据与作业记录
- StudentTutorAgent 查学生画像与错题记录
- LearningAnalyticsAgent 查考试成绩与作业完成情况

### 5.3 第三阶段：按需引入 Vector DB

在出现明确语义召回需求后，再引入：

- `pgvector`：适合已采用 PostgreSQL 的项目，接入成本低
- `Qdrant`：适合独立向量检索服务

推荐最先接入的资源类型：

1. 教材正文切片
2. 优秀教案与教学活动案例
3. 题目解析 / 错题解析
4. 教研资料与课件文本

不建议一开始就把所有数据都向量化。

## 6. 推荐架构

### 6.1 当前推荐基础架构

```text
Workflow Node
-> Business Agent
   -> Service Layer
      -> PostgreSQL Repository
      -> Redis Repository
      -> Skill Layer
   -> LLM Client
-> SafetyGuardAgent
-> FinalizeOutput
```

### 6.2 后续可演进架构

```text
Workflow Node
-> Business Agent
   -> ResourceService
      -> PostgreSQL Repository
      -> Redis Repository
      -> Full-text Search
      -> Vector Repository (optional)
   -> Skill Layer
   -> LLM Client
-> SafetyGuardAgent
-> FinalizeOutput
```

设计原则：

- 向量检索是可插拔层，不是基础前置条件
- Agent 只做编排，不直接耦合底层数据源
- Service 负责资源组织
- Repository 负责具体数据访问
- Skill 负责外部系统能力接入

---

## 7. 业务判断口诀

可用以下一句话快速判断：

- **我知道要查什么字段** -> `PostgreSQL / API`
- **我知道主题，但不知道哪段内容最相关** -> `Vector DB / RAG`
- **候选材料本来就不多** -> `Long Context`
- **既要精确过滤又要语义召回** -> `Hybrid Retrieval`

---

## 8. 对本项目各 Agent 的建议

### 8.1 TeachingDesignAgent

优先依赖：

- `CurriculumService`
- `TextbookService`
- `LessonPlanService`
- `ResourcePlatformSkill`

可先不用向量库。

当需要从大量历史优秀教案、教学活动案例、教材正文中找“最相似内容”时，再引入向量检索。

### 8.2 HomeworkAgent

优先依赖：

- `QuestionBankService`
- `HomeworkPlatformSkill`
- `StudentProfileService`

前期以结构化筛题、题库标签过滤、作业记录为主。

当需要按错因、能力层级、题目讲解相似度做推荐时，再考虑向量检索。

### 8.3 StudentTutorAgent

优先依赖：

- `StudentProfileService`
- `QuestionBankService`
- `HomeworkPlatformSkill`

如以学生画像、错题记录、知识点掌握度为主，可先走结构化资源。

如后续需要从大量解析文本中匹配“最适合当前学生”的解释片段，可引入向量召回。

### 8.4 LearningAnalyticsAgent

优先依赖：

- `LearningAnalyticsService`
- `ExamSystemSkill`
- `HomeworkPlatformSkill`
- `StudentProfileSkill`

该 Agent 以结构化统计分析为主，通常不应把向量数据库作为首要能力。

### 8.5 SafetyGuardAgent

主要依赖：

- 规则
- 策略配置
- 黑白名单
- 安全审查 Prompt

该 Agent 通常不需要向量数据库。

## 9. 后续实施建议

### 9.1 近期建议

按以下顺序推进：

1. 完善 `Service / Repository / Skill` 分层
2. 先让结构化资源接入跑通
3. 先让外部系统能力调用跑通
4. 增加基础缓存能力
5. 对各 Agent 建立最小可用资源访问链路

### 9.2 中期建议

在第一阶段稳定后，再逐步增加：

- 全文检索
- 资源过滤策略
- Prompt 上下文裁剪策略
- 检索结果缓存
- 检索来源可追踪能力

### 9.3 后期建议

仅在确认语义检索确有价值后，才增加：

- 文档切块与 embedding 流程
- 向量索引构建
- 检索融合与 rerank
- 检索效果评估指标

---

## 10. 最终建议

对于本 K12 教学 Agent 项目，推荐遵循以下原则：

> **先做好结构化资源接入、外部系统封装和长上下文编排，再按实际需求补充向量检索，而不是一开始就以 RAG 为基础架构。**

这条路径更符合：

- 当前项目规模
- 教育业务数据特征
- 2026 Agent 项目主流实现方式
- 最小可行、可持续演进的工程实践
